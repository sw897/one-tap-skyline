## 当前适配条件与推荐方案

本轮实际只读检查：本机Docker客户端/引擎29.8.2，Linux x86_64引擎可连接，Compose5.5.1可用，OpenSSH客户端存在；没有构建/运行项目容器或登录服务器。Sites仍active/public/owner/12，唯一原午夜任务启用。目标云服务器、域名、端口及资源未检查。

现有app路由直接导入cloudflare:workers，API使用D1/R2，start/preview启动本地Wrangler；现有构建输出需要服务器适配。推荐一套源码、单实例Node.js游戏服务、SQLite数据库和照片文件卷，Caddy提供同源HTTPS入口；保留Sites的构建目标作为开发路径。

### Docker适配必须补齐的契约

现在的Workers构建物不能直接当作Node服务启动；测试中的SqliteD1仅是故障测试替身，不是已完成的生产适配。P6先形成不依赖cloudflare:workers的服务入口和共用前端构建入口，再锁定一个在目标Linux/CPU架构实际通过的Node/SQLite驱动及镜像摘要。两种目标共用规则、楼体与API业务，不把测试替身直接认定为生产实现。

适配清单包含：SQL外键和窗口排名、JSON/RETURNING、绑定值与空结果、first/all/run返回值、changes含义、单事务batch与故障回滚；HTTP正文上限和流转换、超时、响应状态/媒体/缓存头、匿名cookie和可信公网Origin；文件put完成可见、get的正文/metadata、分页list/cursor、批量delete和缺失对象的幂等结果。对象键由程序生成并限制到照片卷，不能把URL片段直接当文件路径。上述均以实际使用到的D1/R2契约为准。

Compose只有一个游戏服务实例；SQLite操作和游戏维护共用受控连接/事务入口，不先做水平扩展。初始化按原SQL顺序且只执行缺失版本，启动失败不自动删库。照片写临时文件后原子改名，进程被中断时由维护任务回收残留。卷和工作目录使用固定容器路径、受限权限；只暴露Caddy的80/443，游戏端口留在Compose内部网络。服务器/域名/TLS、磁盘空间和时钟同步须实测。镜像只包含锁文件安装产物、必要源码和构建物；不发送本机node_modules、交接包、私有记录、真实照片或.env。

### 午夜清空的执行与并发边界

按服务器UTC时间计算北京时间日界，不能依赖浏览器时钟或仅设置容器TZ。服务启动先完成补偿，后台维护循环检查日界与草稿到期；请求也补偿。容器/服务器停止期间无法在00:00执行：恢复后先清旧日再开放写入，此情况明确记为延迟执行，不声称准点。任务记录计划时间、实际开始/结束、数据范围、剩余对象与重试结果，删除失败要可重试且可见，不能吞掉错误后记成功。

业务、上传写后检查、后台维护与受控时钟验证共用一个服务端时钟入口，检查现有context.now与Date.now混用处，避免测试时钟/日切时间不一致。午夜单次定时器按nextShanghaiMidnight重新计算，维护循环补偿迟到/漏触发；不能把定时器已注册当作准点清理成功。

现有数据库日标记在batch内更新，但“请求进入时检查一次”不足以证明跨午夜安全。P6须为写入捕获游戏日/城市epoch，并在最终提交事务再次校验；日切持有同一写入/维护边界，旧局/旧署名/旧照片保存返回已重置，不得用旧凭证重新产生昨日作品。新日数据仅在日切后登记；新日photo keys使用新日命名空间。

数据库清空与文件删除不是一个可回滚事务。先原子推进日标记并清旧游戏记录，使旧媒体立即不可访问，再按旧日键前缀清理文件；“逻辑重置完成”和“物理文件清理完成”分别记录。已开始的旧日上传必须在文件写入后再次检查日界，清理自身旧文件并拒绝保存；后台重复扫描旧前缀，覆盖晚到文件和分页删除失败。只删除当前日界之前的对象，重试不能清新日文件。草稿每轮按4小时或午夜更早的截止时间处理，无访问也清理。以上是P6待实现和验证的边界，不宣称现有Sites已通过。

## 实施顺序

1. 用户确认修订计划后，完成上述Node入口、SQL事务/文件/日切边界与Docker构建；检查现有配置、请求、cookie、照片响应和规则接口能够复用。出现平台兼容问题先修适配，不修改玩法来绕过。
2. 形成可复现本地Compose候选，完成必要编译、启动、健康检查和存储/定时任务开发检查；测试数据使用隔离的本地卷，保留真实日志。这个步骤不是完整阶段验收。
3. 用户提供目标服务器与域名后，只读盘点系统、CPU架构、磁盘、Docker/Compose、已有服务与80/443占用。部署范围具体后，在安全渠道接收SSH材料，实施明确目录内的部署、HTTPS和真实公网入口；记录实际URL或阻塞。
4. 交用户手工体验容器/公网版，修正实际反馈。现有Sites的受众、写入和午夜任务在切换决定确认前保持；不把Docker的新空城与Sites自动同步。
5. P6开发完成后安排P1至P6统一验收，修复失败并保留失败/复测证据。验收范围与缺口明确后，执行最终入口切换、归档部署材料和培训案例。
