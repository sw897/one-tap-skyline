## 午夜清空及在途请求

1. 采用统一服务端UTC时钟计算北京时间日界；业务、定时维护、照片写后复核及测试使用同一时钟入口，消除context.now/Date.now混用。定时器按nextShanghaiMidnight计算，下次重算；维护循环、启动和请求补偿漏执行。停止期间不能00:00执行，恢复后补偿须记实际延迟。
2. 在受控写入边界捕获并复核游戏日和城市epoch，覆盖城市初始化、匿名登记、开局/取消、成绩/署名/颜色提交、照片准备/保存/撤回及有关限流写入。读取慢请求正文或图片解码完成后重新取时；最终保存短事务再检查期望游戏日/epoch。旧日凭证/局次只能返回已重置或失效，不能复活昨日作品。提交沿用当日局次验证，不再要求扫码；新页与开局仍必须带当日entry。
3. 照片按“短事务登记准备 → 事务外文件IO → 短事务复核并关联”执行。上传不得占用日切锁；写入跨午夜时拒绝关联并清理自身旧日文件。失败清理的旧文件保留pending并由旧前缀扫描补偿；新日文件不能因重试误删。
4. 日切短事务原子推进基础设施日标记并清空全部旧游戏记录。旧媒体状态立即失效；随后分批删除旧日照片、缩略图、临时文件及文件元数据。草稿无人访问也按4小时或午夜更早截止清理，不依赖手机请求或Sites云任务。
5. 数据库事务与文件系统删除不能视作一个可回滚事务。分别记录“逻辑重置完成”“旧媒体不可访问”“物理文件清理完成”；全部旧对象处理完成才报告完整清空。分页、删除失败、晚到文件均需重试，pending不写成功；日志只记时间、数量、错误码和重试结果，不保留照片或完整玩家请求。

必要开发检查包括跨午夜慢正文/上传、多个触发源同时到期、原子提交回滚、分批清理超过单批、文件删除失败/重试、晚到旧日文件、停机跨日补偿、新日数据/文件保留。首次开服及每日换码以服务端状态为准，客户端时钟不能提前/延后清库。真实北京时间00:00无人访问的一次执行与可控时钟检查分别留证；不能用定时器注册或模拟时间通过代替真实结果。
