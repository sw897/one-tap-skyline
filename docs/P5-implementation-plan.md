## 场景与楼体表现

已确定“明亮滨水现代城市”：浅色街道、路沿和标线、行道树、公共广场/公园、滨水步道与简化桥梁；通过日光、轻雾、接触阴影和层次建立城市感。默认增加少量低矮通用公共建筑，并保留关闭它们、只显示道路/公园/水岸的配置。公共建筑不占玩家地块、人数或排名，没有玩家署名/照片。使用代码几何、实例化景物和通用材质，不复制私有概念图或引入未经审核的品牌资产，不做交通模拟。

玩家楼继续用同一TowerModel/buildTower，逐层裁切、局部坐标、宽深、基座、层高和照片立面一致。风格变化采用材质、窗线、边缘和屋顶装饰，不改变裁切规则或另造分数不对应的主体。全景与近景通过相机适配真实高度，不额外抬高低分楼或拼接前后两局。

空城仍有道路、水岸、公园和公共景观，明确“今日0栋玩家建筑”；连接失败时显示等待连接，不能用模拟玩家/成绩填充真实城市。未开放分区呈现绿地或公共景观，不显示可入城空位，不参加巡游统计。设计示意中的楼层、人数和二维码不作实际指标。

## 分区、开放与稳定地块

借鉴主题园区的分区辨识和连接方式，采用主环路、滨水支路、广场节点及不同尺度的街区；住宅街区可局部沿直路排列，滨水和公园边界采用弧形、错位与不同朝向，避免整座城市成为矩形棋盘或随机散点。每个玩家位置必须有可达街道和足够的基座间距，不跨道路/水域或与公共设施重叠。参考入口为[北京环球度假区官方地图](https://www.universalbeijingresort.com/en/map)与[上海迪士尼官方地图](https://www.shanghaidisneyresort.com/zh-cn/experience/?map=true)；本方案使用原创通用城市布局，不复制具体乐园地图、建筑或品牌主题。

建议起步开放5区，以海湾广场、公园街区、滨水商务、运河里、绿荫街区等中性名称区分；容量初值为10/12/14/11/13，合计60，承接原60栋基线。其余5区预留扩展；每区容量10–16，10区全开时配置容量为100–160，绝对上限160个玩家地块。初始5区和具体容量是本次建议值，不冒称用户逐项指定。20并发基线保留，开放更多地块不等于已经验证更高并发。

布局蓝图为每个plotId定义分区、固定位置和朝向，楼体只做整体平移/旋转，模型内部几何不变；分配采用服务端开放地块列表，仍跳过13号公共预留编号。同一日开区/改外观不重建身份、署名、颜色或最佳楼；日切仍按现有规则清空全部游戏数据。此方案替代上一版“保留8×8坐标”的约定：建议在正常北京时间00:00日切后的新城启用新布局，不提前清库，不把旧网格与新分区坐标混用于同一日。

开放数量由受控的服务端运行时配置指定，不新增公开开区/清库接口或管理后台。当日保存有效布局与版本；只可追加开放预定分区，不缩减、改坐标或重排已开放区。新区追加稳定地块、更新容量与city revision；楼层变化、排名变化和开区均不移动已入城楼。需要改蓝图或区容量时在下一次正常日切生效。服务端入城原子操作使用同一开放列表，满城明确提示；客户端URL不能绕过容量或向关闭区分配。

全城快照返回开放区、布局版本和可渲染位置；own范围仅返回自身分区/地块及名次，不扩成全城数据。初始化、容量、楼标签、搜索、聚焦、巡游和事件定位共用映射；布局变化参与版本检查。只追加必要schema，已有SQL/journal不改，不做独立历史兼容迁移工具；每日全游戏重置也清理新增布局状态。

## 按楼层变化的外观与前三名顶饰

建议先做三档，阈值保持可调；同一纯函数按当前作品层数选取样式，游戏、结算、我的楼和城市共用。

| 建议层数 | 外观方向 | 保持的边界 |
| --- | --- | --- |
| 1–9层 | 明亮街区楼，浅色实体墙、暖窗和清楚的层间线 | 保留玩家主色、每层裁切和真实宽深 |
| 10–24层 | 现代商务楼，冷暖玻璃窗线、轻量竖向饰条 | 饰条随逐层退台，不跨悬空裁切，不遮照片 |
| 25层及以上 | 城市地标风格，更清晰的玻璃/竖线节奏与简洁屋顶收边 | 不加虚构楼层、裙楼或额外主体高度，不扩大真实顶面 |

前三名依据服务端官方rank添加金/银/铜三档通用灯环或几何冠饰，随排名变化增删。沿用同分并列1、1、3：并列者使用同等级装饰，缺失名次不人为补位，不暗改成唯一领奖席。顶饰随真实可用顶面缩放；极窄楼顶简化为小型标记，不扩顶或补台。装饰不计楼层/成绩，侧栏成绩及主体高度仍为baseHeight + floors × layerHeight；取景包围盒可包含顶饰。

游戏与未入城结算没有已确认全场名次时不预授顶饰；大屏和“我的楼”按最新取得的官方名次使用同一装饰器。手机不为更新顶饰恢复全城轮询，重新查看时只读取自身快照。照片保留原来的下部真实立面位置，成绩事件与名次装饰更新分开，迟到排名/照片响应不恢复旧装饰。

## 镜头、布局与找楼

大屏入口沿用/?mode=display&view=city。推荐城市视区约72%宽、侧栏约28%；相机按实际城市视区与最高楼包围盒取景，预留标签/控件安全区。侧栏含二维码、真实楼数、前10名和最近5–8条动态；镜头移动不移动二维码。标签只保留选中楼、近期事件或当前街区重点楼，减少重叠。

大屏基线已确定为1920×1080、Chrome，单独使用透视相机和受限OrbitControls：拖动环绕、滚轮/按钮放大、辅助平移；限制距离、俯仰和目标范围，保留“回全景”。取景、裁剪距离和漫游边界依据开放区、公共景观与真实楼体包围盒更新，不继续使用8×8固定范围。游戏/个人作品保持原相机操作。现有锁定Three.js包包含该控制器；[官方相机文档](https://threejs.org/docs/pages/PerspectiveCamera.html)、[官方控制器文档](https://threejs.org/docs/pages/OrbitControls.html)支持这些能力，具体构图仍待可运行候选验证。

默认慢速巡游“全景→有玩家的开放分区→公共景观→全景”，空城只巡公共景观，不假造热闹区；每区停留约10秒、转场约2秒，不按人数均分，新增开放区进入后续巡游。手动操作立即接管，空闲20秒后恢复，也可暂停自动。点击排行/标签或按署名、分区/地块号搜索，可聚焦当前完整楼体及照片；新最佳后跟随同一楼ID、按新几何取景。手机只显示自己的分区/地块号，不恢复总览或全城轮询，也不远程抢占大屏镜头。时间、边界和标签数量均为可调初值。

二维码在浏览器本地编码，使用真实站点的手机入口，稳定白底展示并附短链接；不调用外部二维码图片服务、不使用概念图二维码。正式城与测试城入口明确区分，待P6再切最终域名。没有真实扫码结果时只记录二维码已生成，不宣称投屏扫码通过。

## 真实事件与同步边界

| 有效提交结果 | 大屏行为 |
| --- | --- |
| 首次入城 | 原地出现完整新楼，简短欢迎与地块提示 |
| 严格超过个人最佳 | 用完整新局几何原地更新并长高，提示旧层数→新层数 |
| 严格超过提交前全场最高 | 优先显示全场新纪录与短暂高亮；同次提交只播一个主要提示 |
| 空城首楼/并列最高 | 首楼按首次入城；并列不算全场新纪录，名次沿用1、1、3规则 |
| 低/同分、重复、无效或满城未入城 | 不生成增长/纪录事件，保留既有真实状态 |
| 换图、撤回或到期 | 更新/移除贴图，不触发成绩增长或纪录播报 |

建议在既有成绩条件提交的同一D1批处理中追加有界city_events记录，捕获提交前最高分、事件ID/runId、城市epoch、版本、目标楼、前后层数及服务器时间，避免靠两次快照猜测中间纪录。全场判定必须在事务内取值；幂等重试不重复写事件。仅追加必要schema，不改已应用SQL，不新增身份恢复、管理角色或备份/兼容迁移工具。[D1批处理文档](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)说明批处理事务/失败回滚；这是拟采用的实现方式，尚未测试。

大屏沿用约3秒轮询，在all-city读取中附带有界事件游标/结果，尽量同批读取一致的城市、排名与事件；手机own范围不接收事件流。首次打开只显示当前城和近期动态，不逐个重播旧纪录。建议每城保留当日最近200条事件、每次最多40条；游标缺口/断线恢复以最新快照追平，旧动态不连续抢镜。

动画按楼ID并行管理；最新动态保留真实发生时间，主画面最多一个提示/聚焦，待播队列最多20条，同楼合并到最新最佳。过时事件不把楼变回旧几何；展示前校验当前epoch、目标楼和bestRunId。全场提示优先，手动查看期间先在侧栏提示；不会每次提交都强制镜头跳转。事件排队等待与数据同步时延分开记录。

照片仍按当前资产/装饰版本读取，不复制图片到事件记录；远景仅缩略图，选中楼才用大图，撤回/到期后释放纹理。网络异常保留上次有效城及更新时间；首次无数据、恢复、后台/前台和重试有明确状态。午夜清空新增事件/当日布局状态，并清理客户端队列、排名顶饰、高亮、选择和旧纹理，按新日有效配置回到公共景观；epoch/布局版本/请求世代保护迟到响应。保留现有00:00任务，不新建重复任务，不增加逐帧观战或相机同步服务。
